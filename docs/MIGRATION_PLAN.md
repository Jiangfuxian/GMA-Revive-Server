# 幻书工程迁移为龙族工程

## 已完成

- 保留原 GitHub 仓库地址与仓库历史。
- 建立原幻书工程备份分支：`backup/huanshu-pre-dragon-2026-11-20`。
- 建立独立迁移分支：`dragon-card-migration`。
- 检查用户提供的龙族 APK：ZIP 完整性通过，读取到 Android Manifest。
- 确认目标客户端为 UE4.27.2、包名 `com.zulong.drc.mi`，UE4 原生库为 ARM64。

## 阶段 1：客户端启动验证

1. 在 ARM64 Android 真机安装原 APK。
2. 采集首次启动日志，区分安装失败、UE4 初始化失败、纹理格式失败、资源解包失败和网络登录失败。
3. 检查启动画面、UE4 GameActivity、资源初始化、登录入口。
4. 记录设备型号、Android 版本、可用内存、图形驱动和日志。
5. 只有确认原 APK 可在目标设备启动后，才进入客户端改造。

## 阶段 2：资源结构研究

1. 分析 `assets/res_base/package/` 的封包格式和目录索引。
2. 分析 APK 内的 `assets/main.obb.png` 及资源版本信息。
3. 先做只读解析和资源清单，不修改原始资源。
4. 对提取结果计算哈希，建立可重复验证的资源索引。
5. 不把 Dragon 资源伪装成 NPK，也不直接覆盖幻书资源文件。

## 阶段 3：网络与服务端兼容性

1. 识别登录、区服发现、热更新、资源校验和游戏网关的调用顺序。
2. 区分客户端 SDK、官方服务端接口和游戏业务协议。
3. 先建立协议记录与只读诊断工具。
4. 是否开发离线服务端，取决于协议可验证程度、所需服务端数据和实现成本；不能仅凭 APK 资源包推定可离线运行。

## 阶段 4：安卓适配

1. 优先以 K70 的 ARM64 真机作为基准设备。
2. 先测试原 APK，不先改包名、不先改 Manifest、不先替换 so。
3. 再评估屏幕比例、权限、存储路径、图形兼容和后台行为。
4. x86_64 GitHub 模拟器只作为辅助环境；ARM64 UE4 库可能无法在其上执行。
5. 每完成一个可验证阶段，保存构建产物、日志和复现步骤。

## 风险与不做事项

- 不把原幻书 Go/PostgreSQL 业务逻辑冒充为龙族后端。
- 不在没有备份的情况下删除原始 APK、分卷或资源。
- 不把完整商业游戏 APK 或未授权资源提交到公开 Git 仓库。
- 不宣称“已适配”“已离线”或“可运行”，除非对应真机/模拟器日志实际通过。
